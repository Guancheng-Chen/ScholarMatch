## Accessibility Report

**Audience.** Students, researchers, and academics using a desktop app to find collaborators, discover research opportunities, and message potential matches.
**Model.** We follow the **social model of disability**: barriers live in the product environment, so we design the default UI for everyone—no separate "accessible mode".

### Universal Design principles → current status

| Principle                      | Status      | What's in ScholarMatch today                                                                                                                                        | Next steps (high-impact)                                                                                                          |
| ------------------------------- | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| **1. Equitable Use**            | Partial     | One UI for all users; no segregated interface. Nav items and cards pair an icon with a text label rather than icon-only controls (`NavigationBar`, `RecommendUserCard`, `MatchedUserCard`). | Add programmatic **name/role/state** (`AccessibleContext`) to custom Swing components; none is set today.                          |
| **2. Flexibility in Use**       | **Improving** | Single hardcoded light theme (`scholarmatch-light.properties`, FlatLaf); font sizes are fixed point values set throughout view code, not user-adjustable.             | Add a **dark theme** and a real **zoom/text-scale** setting; audit/complete keyboard-only navigation (see below).                   |
| **3. Simple & Intuitive**       | Partial     | Plain labels ("Recommend", "My Postings", "Messages"); predictable CRUD-style flows for login, matching, postings, and chat.                                          | Brief first-run guidance for new users; standardize error-message wording across views.                                            |
| **4. Perceptible Information**  | Partial     | Consistent teal-green academic color palette; icons **and** text labels on nav/cards.                                                                                 | Verify contrast ≥ **4.5:1** against the palette; associate form inputs with labels; add descriptions for logo/illustration assets. |
| **5. Tolerance for Error**      | **Strong**  | **Logout confirmation dialog** (`NavigationBar`, `JOptionPane.YES_NO_OPTION`, warning icon) and a custom **`ConfirmationDialog`** component gate destructive actions (e.g. account deletion, posting actions). Inline error labels bound to view-model state in `LoginView`/`RegisterView`; `JOptionPane` alerts elsewhere. | Bring the rest of the app onto the inline error-label pattern instead of modal alerts; link errors to the specific field.          |
| **6. Low Physical Effort**      | Partial     | Standard forms and clicks; no drag/long-press interactions anywhere in the UI.                                                                                         | Add keyboard shortcuts for common actions (submit, next/previous card) to cut mouse dependency.                                    |
| **7. Size & Space for Use**     | Partial     | The main application window is resizable by default (no `setResizable(false)`); layout mixes `BorderLayout`/`BoxLayout` with `GridBagLayout`/`GridLayout`/`CardLayout`. | Many dialogs and cards use fixed `setPreferredSize`/`setMinimumSize`, which breaks down at small window sizes—replace with layout-driven sizing where practical. |

**Per-principle notes**

* **Equitable Use:** One UI for all; icon+text labeling already benefits everyone. • Future: `AccessibleContext` naming across custom components (currently absent — confirmed via source search).
* **Flexibility in Use:** Currently the area with the most room to grow — no dark theme, no zoom, and no custom key bindings, mnemonics, or `InputMap`/`ActionMap` usage were found anywhere in `src/main/java`, so keyboard-only users rely entirely on Swing's default tab order. • Future: dark theme, text scaling, and an explicit, tested keyboard path for every core task.
* **Simple & Intuitive:** Clear labels, predictable flows for matching/postings/messaging. • Future: first-run tips, consistent error copy.
* **Perceptible Information:** Single high-contrast-intent palette, icon+text pairing. • Future: verify contrast, add `setLabelFor` associations, alt-text for imagery.
* **Tolerance for Error:** **Logout requires confirmation**, destructive posting/account actions route through `ConfirmationDialog`, and login/register surface inline, view-model-driven error text. • Future: extend the inline-label pattern app-wide; field-linked validation.
* **Low Physical Effort:** No precision gestures required. • Future: shortcuts for the most frequent actions.
* **Size & Space:** Main window resizes; two modal auth dialogs are intentionally fixed-size. • Future: reduce fixed `setPreferredSize`/`setMinimumSize` usage so cards and dialogs reflow at small sizes.

**Market / Audience.**
If we licensed ScholarMatch commercially, our primary customers would be **university career centers, graduate schools, and research offices** looking for a lightweight way to help their students and faculty find collaborators — as opposed to a general-purpose social network. The core end users are **graduate students and early-career researchers** trying to find a co-author, a mentor, or a research-group opening in their field, plus **faculty and industry researchers** posting opportunities and reviewing applicants. It also suits **undergraduates** looking for a first research experience, since the recommend feed and posting board don't assume an existing publication record. Because the app is a self-contained desktop client rather than a hosted social platform, it would also appeal to institutions that want to run their own instance against their own server rather than send student data to a third-party network.

**Access & ethics.**
Several groups are less likely to be able to use ScholarMatch as it stands today, beyond the "wrong audience" sense above. The app is **English-only** (`Locale.setDefault(Locale.ENGLISH)` in `ScholarMatchApp`), which shuts out non-English-speaking students and researchers even though international researchers are a natural part of the target audience. With **no dark theme, no text-zoom, no keyboard-only path, and no Swing `AccessibleContext` names/roles** on any custom component, low-vision, keyboard-only, and screen-reader users face real barriers using it at all — this isn't a hypothetical edge case, it's most of the checklist in the table above. The **institution picker is a closed list** of roughly 1,000 institutions sourced from the QS World University Rankings and a curated set of major research institutes (`institutions.csv`); a researcher at an institution outside that list, an independent scholar, or someone at a smaller or non-Western institution the rankings underrepresent has to select a generic "Other" — a small design choice that quietly signals whose institutional affiliation the app was built assuming. And because the client talks to a hosted server by default, people without a reliable, unmetered internet connection are functionally excluded from the real (non-demo) experience — the offline mode is an in-memory fallback for demos, not a substitute for genuine offline-first access. None of these are exotic failure modes; they track fairly directly onto the access-and-inclusion themes from this term's ethics modules — the people most excluded tend to be the people already least represented in whichever "default" a product is built around.
