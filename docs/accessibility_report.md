## Accessibility Report

**Audience.** Students, researchers, and academics using a desktop app to find collaborators, discover research opportunities, and message potential matches.
**Model.** We follow the **social model of disability**: barriers live in the product environment, so we design the default UI for everyone—no separate "accessible mode".

### Universal Design principles → current status

| Principle                      | Status      | What's in ScholarMatch today                                                                                                                                        | Next steps (high-impact)                                                                                                          |
| ------------------------------- | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| **1. Equitable Use**            | Partial     | One UI for all users; no segregated interface. Nav items and cards pair an icon with a text label rather than icon-only controls (`NavigationBar`, `RecommendUserCard`, `MatchedUserCard`). | Add programmatic **name/role/state** (`AccessibleContext`) to custom Swing components; none is set today.                          |
| **2. Flexibility in Use**       | **Weak**    | Single hardcoded light theme (`scholarmatch-light.properties`, FlatLaf); font sizes are fixed point values set throughout view code, not user-adjustable.             | Add a **dark theme** and a real **zoom/text-scale** setting; audit/complete keyboard-only navigation (see below).                   |
| **3. Simple & Intuitive**       | Partial     | Plain labels ("Recommend", "My Postings", "Messages"); predictable CRUD-style flows for login, matching, postings, and chat.                                          | Brief first-run guidance for new users; standardize error-message wording across views.                                            |
| **4. Perceptible Information**  | Partial     | Consistent teal-green academic color palette; icons **and** text labels on nav/cards.                                                                                 | Verify contrast ≥ **4.5:1** against the palette; associate form inputs with labels; add descriptions for logo/illustration assets. |
| **5. Tolerance for Error**      | **Strong**  | **Logout confirmation dialog** (`NavigationBar`, `JOptionPane.YES_NO_OPTION`, warning icon) and a custom **`ConfirmationDialog`** component gate destructive actions (e.g. account deletion, posting actions). Inline error labels bound to view-model state in `LoginView`/`RegisterView`; `JOptionPane` alerts elsewhere. | Bring the rest of the app onto the inline error-label pattern instead of modal alerts; link errors to the specific field.          |
| **6. Low Physical Effort**      | Partial     | Standard forms and clicks; no drag/long-press interactions anywhere in the UI.                                                                                         | Add keyboard shortcuts for common actions (submit, next/previous card) to cut mouse dependency.                                    |
| **7. Size & Space for Use**     | Partial     | The main application window is resizable by default (no `setResizable(false)`); layout mixes `BorderLayout`/`BoxLayout` with `GridBagLayout`/`GridLayout`/`CardLayout`. | Many dialogs and cards use fixed `setPreferredSize`/`setMinimumSize`, which breaks down at small window sizes—replace with layout-driven sizing where practical. |

**Per-principle notes**

* **Equitable Use:** One UI for all; icon+text labeling already benefits everyone. • Future: `AccessibleContext` naming across custom components (currently absent — confirmed via source search).
* **Flexibility in Use:** Currently the weakest area — no dark theme, no zoom, and no custom key bindings, mnemonics, or `InputMap`/`ActionMap` usage were found anywhere in `src/main/java`, so keyboard-only users rely entirely on Swing's default tab order. • Future: dark theme, text scaling, and an explicit, tested keyboard path for every core task.
* **Simple & Intuitive:** Clear labels, predictable flows for matching/postings/messaging. • Future: first-run tips, consistent error copy.
* **Perceptible Information:** Single high-contrast-intent palette, icon+text pairing. • Future: verify contrast, add `setLabelFor` associations, alt-text for imagery.
* **Tolerance for Error:** **Logout requires confirmation**, destructive posting/account actions route through `ConfirmationDialog`, and login/register surface inline, view-model-driven error text. • Future: extend the inline-label pattern app-wide; field-linked validation.
* **Low Physical Effort:** No precision gestures required. • Future: shortcuts for the most frequent actions.
* **Size & Space:** Main window resizes; two modal auth dialogs are intentionally fixed-size. • Future: reduce fixed `setPreferredSize`/`setMinimumSize` usage so cards and dialogs reflow at small sizes.

**Market / Audience.**
ScholarMatch targets **students, researchers, and academics** who want to find collaborators and research opportunities based on shared interests—an "Academic Matchmaking and Collaboration Network." It suits users who prefer a **focused desktop** experience for browsing recommended matches, posting or applying to research opportunities, and messaging collaborators directly. The client is a standard Java desktop app (Maven/Swing) and, by default, talks to a hosted server over HTTP; an `OFFLINE_MODE`/in-memory fallback exists for demos when the server is unreachable, but this is not persistent local storage (see `docs/api/BACKEND_SERVER_API.md`).

**Access & ethics.**
Today the app is **English-only** (`Locale.setDefault(Locale.ENGLISH)` is set deliberately in `ScholarMatchApp`), which is an environmental barrier for non-English-speaking students and researchers who are otherwise the app's core audience. It offers **no dark theme and no text-zoom/scaling**, so low-vision users have no in-app way to increase contrast or enlarge text beyond what their OS provides. No custom keyboard shortcuts, mnemonics, or focus-traversal handling exist, and no Swing `AccessibleContext` names/roles are set anywhere, so **screen-reader and keyboard-only users currently face real barriers** navigating custom components (cards, dialogs, nav bar). We are closing gaps by prioritizing a keyboard-only path for core tasks, accessible naming for custom components, and a dark/high-contrast theme. Because the client is online-by-default, users without reliable internet access are also excluded from real data; a fully local/offline-first mode is a longer-term goal beyond today's in-memory demo fallback.
